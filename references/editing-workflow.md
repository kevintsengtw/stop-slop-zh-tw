# 編輯工作流程

這份流程負責控制改寫範圍與內容保真。詞語和句型判斷仍以 `phrases.md`、`structures.md`、`terminology.md` 為準。

## 1. 先決定任務模式

### Annotation mode：只找問題

使用者要求「只標問題」「先不要改」「看看哪裡像 AI」時啟用。

依出現順序列出問題，每項包含：

- **位置**：檔案行號，或聊天文字的段落與原句。
- **問題**：命中的詞語、結構、語感或台灣用語問題。
- **理由**：這個位置為什麼影響閱讀；不要只說「有 AI 味」。
- **方向**：建議刪除、改具體、調整句型、校正用語或保留觀察。

不要提供完整替換句，不要附一份順手改好的全文，也不要更動檔案。短文可以列完所有明顯問題；長文依嚴重程度分成「優先處理」和「次要調整」，但不要用「其餘類似」省略無法定位的問題。

### Rewrite mode：改寫

使用者明確要求改寫時，才輸出改寫版或修改檔案。先記錄原文需要保留的內容，再套用去 AI 味與台灣用語規則。

若使用者同時要求「直接改，不用說明」，可以省略問題清單，但不能省略內部的保真回讀。

## 2. 建立保留項目

改寫前先從原文記下：

- 人名、組織名、產品名、技術名詞與版本號
- 數字、日期、比例、價格、期限與條件
- URL、檔案路徑、指令、程式碼與 API 名稱
- 引號內的原話、明確標示的引用與來源歸屬
- 作者的判斷、情緒、立場與不確定程度
- 事件順序、因果關係與比較對象

這些內容可以調整周邊句法，不能擅自改值、換來源、增強語氣或改變責任歸屬。中國用語若出現在引言、程式碼、產品名稱或刻意討論的詞語中，也不要自動替換。

## 3. 長文防縮水

跨多段、含完整章節或約千字以上的內容，預設視為長文。先辨認每一段的功能，例如提出問題、交代背景、提供案例、列出限制、說明結果或轉折。

改寫時遵守：

- 保留標題層級、段落順序與論述路徑，除非使用者要求重整架構。
- 原文的案例、限制條件、反例與但書都要能在改寫版找到。
- 不把多個資訊點合成一句空泛總結，也不把散文擅自改成清單。
- 承擔時間、因果或觀點轉折的句子不能因為短而刪除。
- 純套話可以刪；若刪掉整句或整段，交稿時簡短列出刪除位置與理由。
- 只有使用者明確要求摘要、縮寫、字數上限或平台限長時，才壓縮資訊。壓縮後仍需說明省略了哪些部分。

## 4. 人味邊界

可以做的事：

- 調整句長與停頓，讓節奏不再整齊劃一。
- 刪除清喉嚨、假高潮、空泛結論與重複說明。
- 保留作者已經寫出的口語、猶豫、自嘲、偏好和情緒反應。
- 把抽象說法換成原文已提供的事實。

不能做的事：

- 把第三方資料改寫成「我自己的經驗」。
- 為了具體而編造數字、案例、來源、職稱或時間點。
- 替作者增加「我以前錯了」「我後來才發現」等不存在的經歷。
- 把中性說明改成支持或反對，或替作者選擇原文沒有選定的立場。
- 用自創口頭禪、玩笑或情緒模仿不存在的個人風格。

原文太空泛時，依序選擇：

1. 刪除不承載資訊的句子。
2. 改成原文能支持的最低限度陳述。
3. 論述因此缺一塊時，標示「〔待作者補充：具體需要什麼〕」。

## 5. 保真回讀

交稿前把改寫版和原文並排核對：

1. 每個保留項目是否仍存在，而且內容一致。
2. 每個主要資訊點是否仍能定位，長文是否少了案例、限制或轉折。
3. 「可能、通常、部分、至少」等程度與範圍是否被改強或改弱。
4. 原文的推測、相關性與因果是否仍維持同一層級。
5. 作者的立場、責任歸屬和引用來源是否改變。
6. 是否出現原文沒有的第一人稱經歷、數字、資料或結論。

任一項不一致，先修正再交稿。完成後只需簡短說明重要刪改與待作者補充處，不必把內部核對清單全部輸出。
