# stop-slop-tw 後續修改計畫

## 目標

在不改變作者資訊、立場與經驗的前提下，強化 `stop-slop-tw` 的排版一致性、掃描準確度、修改安全性與可驗證性。

本計畫不以照抄其他 skill 為目標，而是將可借鑑的設計轉化為符合本專案需求的獨立實作。

## 必要需求

以下規則屬於硬性需求，實作與驗收時不可省略。

1. 中文句子使用全形標點。
2. URL、程式碼與英文句子保留半形標點。
3. 中英文混排時，中文與英文字母或英文縮寫之間必須有一個 U+0020 半形空白。

範例：

```text
使用OpenAI API測試, 結果正常.
↓
使用 OpenAI API 測試，結果正常。
```

下列內容不得因中文排版規則而被改動：

```text
Build failed, please retry.
https://example.com/a,b?x=1
const message = "Hello, world.";
```

## 實作原則

- 先辨識與保護技術內容，再進行標點或空格正規化。
- 優先使用可測試、可重複執行的確定性工具處理機械規則。
- 預設只檢查並顯示差異，只有明確指定時才寫回檔案。
- 修改後必須進行保真回讀，確認資訊、立場、限定語與因果關係沒有改變。
- 改善節奏與人味時，不得替作者新增故事、經驗、情緒或立場。
- 長文盡量逐句對應，不得為了簡潔而擅自濃縮。

## 階段一：建立共用文字保護區解析器

### 工作項目

- 新增共用模組，例如 `scripts/text-regions.mjs`。
- 辨識並保護下列區域：
  - Markdown fenced code block
  - Markdown inline code
  - URL 與 autolink
  - Markdown 連結目標
  - HTML 標籤及屬性值
  - Email
  - 常見檔案路徑
- 讓用語掃描器與後續排版工具共用同一套區域判斷，避免規則分歧。
- 保留區域的起訖位置與類型，供診斷輸出及測試使用。

### 驗收標準

- 保護區內容在檢查或修正前後完全一致。
- Markdown 連結顯示文字可以檢查，但連結目標不得改動。
- 同一輸入重複解析時，區域邊界與類型保持一致。

## 階段二：實作中文排版檢查與修正器

### 工作項目

- 新增 `scripts/zh-tw-typography.mjs`。
- 新增 `references/typography.md`，記錄規則、例外與範例。
- 支援以下模式：
  - `--check`：只檢查，不修改。
  - `--json`：輸出規則 ID、位置、原文片段與建議內容。
  - `--dry-run`：顯示預計修改的差異。
  - `--fix`：明確要求後才寫回。
- 實作中文句子的半形標點轉全形規則：
  - `,` → `，`
  - `.` → `。`
  - `:` → `：`
  - `;` → `；`
  - `!` → `！`
  - `?` → `？`
- 只在能安全判斷配對與語境時處理括號及引號。
- 純英文句子保留或修復為半形標點。
- 中文與英文字母或英文縮寫之間統一為一個 U+0020 半形空白。
- 移除全形標點內側不必要的半形空白。
- 將數字、版本號、日期、時間、小數與單位列為獨立政策，不從中英文空格規則自行推論。

### 驗收標準

- 三項必要需求都有正向與反向測試。
- URL、程式碼、Email、路徑、版本號及小數不被破壞。
- 工具具備冪等性：同一檔案連續修正兩次，第二次不得再產生差異。
- `--check` 與 `--dry-run` 不得寫入檔案。

## 階段三：加入安全寫回與診斷資訊

### 工作項目

- 讓用語掃描器與排版工具回報：
  - 規則 ID
  - 檔案路徑
  - 行號與欄位
  - 原文片段
  - 建議修改
  - 是否位於保護區
- 寫回前產生可檢視的差異。
- 採用暫存檔與原子替換方式寫回，避免中途失敗造成檔案損壞。
- 保留 Annotation mode：只列出問題、位置、理由與建議，不直接改寫原文。

### 驗收標準

- 每個問題都能定位到具體檔案與位置。
- Annotation mode 執行前後，來源檔案內容完全一致。
- 寫回失敗時，原始檔案保持可用且內容不受影響。

## 階段四：補齊文體邊界與保真硬門檻

### 工作項目

- 為以下場景建立規則邊界與測試：
  - 技術文章與教學
  - README 與 API 文件
  - Release notes 與 changelog
  - Pull request、Issue 與程式碼審查
  - 公告、Email 與社群貼文
  - 表格、清單與引用內容
- 區分「提到某個詞」與「實際使用該詞」。
- 收窄 skill 觸發範圍，避免將翻譯、摘要、事實查核與程式碼修改誤判為去除 AI 腔任務。
- 將保真回讀列為修改後的硬性門檻：
  - 資訊不得消失。
  - 立場不得改變。
  - 否定、限制、保留與不確定性不得被弱化。
  - 數字、名稱、引用與因果關係不得漂移。
- 將風格分數定位為診斷資訊，不以固定分數取代人工判斷。

### 驗收標準

- 長文修訂能逐段對應原文，且沒有未說明的內容縮減。
- 引用、專有名詞、數字及作者立場保持一致。
- 技術文體不因追求口語化而失去準確性。

## 階段五：建立 SF／SNF 成對測試與實際應用驗證

### 工作項目

- 建立 Should Fire（SF）案例：規則應觸發。
- 建立 Should Not Fire（SNF）案例：規則不得觸發。
- 至少涵蓋：
  - 中文句子的半形標點。
  - 純英文句子。
  - 中英文之間缺少半形空白。
  - URL、程式碼、Email、路徑與版本號。
  - Markdown 連結顯示文字與連結目標。
  - 只找問題的 Annotation mode。
  - 長文防縮水與保真回讀。
  - 正式公告、引用及技術文件。
- 使用未經 skill 調整的長文作為原始輸入，執行完整修改流程。
- 更新 `evals/longform-application/` 內的原文、修訂文與比較報告。

### 驗收標準

- SF 案例全部觸發預期規則。
- SNF 案例沒有誤判或內容漂移。
- 所有保護區達到零內容變更。
- 原有 Node.js 測試、詞條驗證與 `quick_validate.py` 持續通過。
- 長文比較報告逐項確認資訊、立場、數字及限定語沒有消失或改變。

## 階段六：補齊 skill 完整性

### 工作項目

- 檢查並補齊 `agents/openai.yaml`，使介面描述與 `SKILL.md` 一致。
- 在 `SKILL.md` 中加入排版參考文件與工具的載入條件及操作順序。
- 補充本地安裝與使用方式，但避免讓核心 skill 文件膨脹。
- 為詞條補充來源、判定理由與適用邊界，提升後續維護可追溯性。

## 建議執行順序

1. 共用文字保護區解析器。
2. 中文排版檢查與修正器。
3. 安全寫回與診斷資訊。
4. 文體邊界與保真硬門檻。
5. SF／SNF 測試與長文實際驗證。
6. Skill metadata、文件與詞條來源整理。

前三個階段決定必要排版規則能否安全落地，應優先完成。第四與第五階段負責防止內容失真及回歸，不能在正式啟用自動修正前省略。

## 完成定義

只有在以下條件全部成立時，才視為本計畫完成：

- 三項必要排版規則均已實作並通過成對測試。
- 所有保護區在修正前後完全一致。
- 排版工具可檢查、預覽、輸出 JSON 並安全寫回。
- 工具具有冪等性。
- Annotation mode 不會修改來源內容。
- 長文沒有擅自濃縮，保真回讀沒有發現資訊或立場漂移。
- 現有掃描器、詞條驗證及 skill 驗證全部通過。
- 實際應用比較報告已更新並可供人工查核。
